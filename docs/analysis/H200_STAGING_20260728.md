## Item 5 — AlphaFold structures (priority 5)

Route used: **tar-locally-first**, per the fallback instruction for many small files (47,173 files). `h200_sync.sh` also does this internally (`tar` → chunked/resumable `h200_gpfs_push.sh` → pod-side `tar -x`), but a mid-transfer session reset killed the wrapper's background process, so the remainder was completed manually for full control over the tar's lifecycle:

1. `h200_sync.sh push` built a 10,355,015,680-byte tar (SHA-256 `bb342da0...8f5`) and had uploaded roughly 32 of 39 chunks when the hosting session was reset and the background process was killed.
2. The killed process's own `EXIT` trap fired with a delay and deleted the local tar (observed: present and hash-verified once, then gone ~1 minute later without any explicit action).
3. The tar was **rebuilt** at a fixed, manually-controlled path (`tar -C .../alphafold -cf ... .`, 9.7 s — filesystem cache was warm). It hashed **identical** to the original (`bb342da0...8f5`), confirming `tar` is deterministic for this unchanged source directory on this filesystem.
4. `h200_gpfs_push.sh` was invoked directly (not via `h200_sync.sh`, to reuse the exact same content hash) against the same destination path used in step 1. Because the master-side chunk cache is keyed by the file's SHA-256, **33 of 39 chunks (~85%) were reused ("Reusing verified chunk") from the interrupted run**, and only 6 chunks needed re-upload — a genuine resume, not a restart.
5. The verified tar was extracted inside the pod with `tar -C <dest> -xf <tar>`, then the staging tar (in `/gpfs/.../.h200-transfer/`) and local tar (on the transfer host) were deleted.
